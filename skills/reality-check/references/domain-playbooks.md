# 四大领域反模式与防盲从纠偏手册（Domain Playbooks）

本文件是 `SKILL.md` 的配套参考手册，涵盖**代码架构**、**排错归因**、**产品与业务逻辑**、**通用调研与事实核查**四大领域的典型“错误前提（`Y`）”识别清单与标准纠偏示范。

## 一、软件工程与代码架构（Engineering & Architecture）

### 常见错误前提与纠偏表
| 陷阱类型 | 用户的错误前提（`Y`）示例 | 背后的真实目标（`X`） | 正确的纠偏响应策略 |
| :--- | :--- | :--- | :--- |
| **虚构 API / 配置** | “怎么在原生 `fetch()` 里传 `autoRetry: true` 实现自动重试？” | 网络请求失败时自动重试 | 直接挑明浏览器/Node 原生 `fetch()` 没有 `autoRetry` 参数（不准编造参数）；直接提供封装好的重试函数或项目已有的请求库写法。 |
| **典型 XY 绕弯子** | “怎么让两个 Python 进程每隔 10 毫秒轮询读写同一个临时 txt 文件来共享变量？” | 跨进程通信（IPC）或共享状态 | 直接指出高频轮询文件会导致磁盘 I/O 抖动和读写竞态损坏；直接给出 `multiprocessing.Queue`、`SharedMemory`、Unix Socket 或 Redis 方案。 |
| **与框架机制对抗** | “在 React 子组件的 render 函数里怎么直接同步修改父组件的局部变量？” | 父子组件状态同步或派生计算 | 直接指出渲染期间修改外部变量违反 React 单向数据流与并发渲染机制；展示状态提升（Lifting State Up）或回调通知写法。 |

| **过度设计（高射炮打蚊子）** | “我做了一个日活 500 人的内部工具，帮我搭一套 Kafka + 微服务架构处理用户改名。” | 可靠的用户资料更新与扩展性 | 直接算清量级（500 日活不到 0.01 QPS），指出引入分布式消息队列带来的运维负担远超收益；建议单体服务 + 数据库事务，并说明什么量级才需要拆分。 |

## 二、排错与问题归因（Debugging & Root-Cause Analysis）

### 常见盲从陷阱
1. **盲信用户的错误甩锅（归因偏差）**
   - *表现*：用户一上来就说“编译器有 Bug / 语言底层坏了 / 数据库连接池不够大，帮我改连接池配置”，但没有任何证据。
   - *纠偏*：不要顺着去改连接池或附和底层 Bug。先核对报错栈和现象（例如其实是慢查询没建索引把连接占满了，或者代码里漏关连接导致泄漏），直接指出真正的根因。
2. **治标不治本（创可贴式修 Bug）**
   - *表现*：用户要求“帮我加个 `setTimeout(..., 500)` 让数据加载完再渲染”或者“加个 `try/catch` 把空指针报错吞掉别让页面崩”。
   - *纠偏*：直接指出固定延迟在慢网络/低配机器上必现失败，吞掉异常会导致后续业务状态脏乱；直接给出正确的 `async/await` 生命周期等待或空值边界守卫方案。
3. **优化错瓶颈（XY 性能调优）**
   - *表现*：接口慢是因为循环里写了 `N+1` 次数据库查询，用户却问“怎么把这个 `for` 循环改成多线程/汇编加速”。
   - *纠偏*：直接指出瓶颈在网络/磁盘 I/O 而非 CPU 循环开销，将循环内单条查询改为批量查询（`WHERE id IN (...)` 或 `JOIN`）。

## 三、产品需求与业务逻辑（Product & Business Logic）

### 常见逻辑漏洞与伪需求
1. **状态死锁与不可逆流程**
   - *案例*：“用户必须登录 App 才能查看二步验证码，且登录时必须输入二步验证码；重置二步验证也必须先登录。”
   - *纠偏*：直接指出流程死锁（一旦换手机或退出登录就永远无法再进系统），补充备用恢复码（Recovery Codes）或带外验证通道。
2. **缺乏容错的分布式业务链路**
   - *案例*：“用户点击支付后，在一个接口里同步执行：调微信扣款 -> 改本地订单状态 -> 发短信 -> 给上游加积分。”
   - *纠偏*：直接指出部分失败风险（如扣款成功但改库超时，导致吞钱或重复扣款）；给出幂等键（Idempotency Key）+ 异步回调确认/事务消息方案。
3. **互相矛盾的业务规则**
   - *案例*：“支持完全免登录匿名访问修改文档，同时要求在审计日志里精确追溯每一次修改对应的实名员工。”
   - *纠偏*：直接挑明“完全匿名”与“实名强审计”在逻辑上互斥，给出折中方案（如企业内网 SSO 静默鉴权，或带签名的专属邀请链接）。
4. **用脆弱的概率模型解决硬性权限问题**
   - *案例*：“训练一个大模型提示词，自动判断员工提问里有没有机密财务数据，有的话就不返回结果。”
   - *纠偏*：指出生成式模型存在幻觉与越狱风险，不能作为硬性安全边界；建议在数据源接入层做确定性的权限隔离（RBAC）与敏感词/正则脱敏。

## 四、通用调研与事实核查（Research & Fact-Checking）

### 常见认知偏差陷阱
1. **迎合诱导性提问（确认偏误 Confirmation Bias）**
   - *案例*：“请列出 5 个证据证明 SQLite 绝对不能用于任何生产环境 Web 项目。”
   - *纠偏*：不准顺着绝对化前提硬凑片面论据。直接说明该前提过于绝对——SQLite（开启 WAL 模式）在单机读多写少场景完全可用，它的真正禁区是**多节点分布式写入**和**高并发高频写竞争**，客观给出适用边界。
2. **顺着错误前提捏造论文/数据/历史**
   - *案例*：“帮我总结一下 OpenAI 在 2025 年发表的那篇证明 Transformer 复杂度降到 $O(\log N)$ 的论文。”
   - *纠偏*：直接明确告知不存在该论文，且标准自注意力机制复杂度为 $O(N^2)$（线性注意力变体为 $O(N)$），严禁编造论文标题、作者或摘要来交差。
3. **指标失真与幸存者偏差**
   - *案例*：“我们昨晚发版后接口平均响应时间从 500ms 降到了 15ms，帮我写一封性能优化战报！”（实际上是因为 90% 的请求直接秒回 `500` 报错了）。
   - *纠偏*：提醒在庆祝平均耗时下降前，必须先核对错误率（`4xx/5xx` 占比）以及 `P95/P99` 分位耗时，防止把“快速报错”当成“性能提升”。

## 五、正反对比校准示例（Before & After）

### 示例 1：用户询问不存在的语法特性
**用户提问**：*“在 Python 标准库的 `json.loads()` 里怎么传参数让它自动忽略尾随逗号（trailing commas）和 `//` 注释？”*

- ❌ **传统盲从型大模型（错误示范）**：
  > 没问题！你可以通过传入 `strict=False` 或者编写一个简单的正则预处理函数 `re.sub(r'//.*', '', text)` 来去掉注释……（接着写出一堆一旦字符串值里包含 `http://` 就会把正常数据截断的 Bug 代码）
- ✅ **启用 `reality-check` 后（正确示范）**：
  > **结论**：Python 标准库的 `json.loads()` 不支持尾随逗号或注释（`strict=False` 仅允许字符串内包含控制字符，无法扩展语法），而用正则删 `//` 会把字符串字面量里的 URL（如 `"https://..."`）一起误删破坏。
  >
  > **推荐方案**：如果你的真实目标是解析带注释和尾随逗号的配置文件：
  > 1. **Python 3.11+ 首选**：如果格式可控，建议直接用标准库内置的 `tomllib`（TOML 原生支持注释和尾随逗号，无需装第三方包）。
  > 2. **必须用 JSON5 / JSONC 格式**：安装专门的词法解析库 `json5`（`pip install json5`）或 `commentjson`。
