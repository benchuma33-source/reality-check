# 独立红队子 Agent 交叉验证协议（Red-Team Subagent Protocol）

## 为什么需要独立子 Agent 交叉验证？

单 Agent 在同一上下文中自我检查（Self-Check）有两个物理上限：
1. **上下文锚定污染**：当主 Agent 已经顺着某个思路写了数百行代码或多轮方案，它的自注意力机制会被自己刚生成的历史推理链锚定，极难主动推翻自己。
2. **长对话权重稀释**：当对话超过 15–30 轮后，`SKILL.md` 在上下文中的相对权重被大幅稀释，软约束开始失效。

**解法**：将“干活（Builder）”与“挑刺（Red-Team Critic）”拆到两个**物理隔离的上下文**中。子 Agent 看不到主 Agent 讨好用户的历史过程，只接收【原始目标 `X` + 拟定方案 `Y` + 代码库只读权限】，其唯一 KPI 就是证伪方案 `Y`。

---

## 一、触发红队子 Agent 的条件

满足以下任一条件时，主 Agent 应主动拉起红队子 Agent（无需等用户点名）：
1. **高风险不可逆变更**：涉及生产数据库 Schema 破坏性迁移、鉴权/加密链路重构、计费结算逻辑修改。
2. **长对话复杂叠加（>15 轮）**：用户与主 Agent 已经围绕某个复杂方案反复打补丁超过 3 次仍未彻底跑通（典型的“在错误前提上盖楼”信号）。
3. **主 Agent 存疑但拿不准**：主 Agent 感觉方案有些别扭，但在当前上下文里一时找不到确凿反例。

---

## 二、跨平台调用方式

根据当前运行的宿主环境，选择对应的只读子 Agent 工具：

- **Antigravity**：调用 `invoke_subagent`（`TypeName: "research"`，只读沙箱，隔离上下文，`Role: "Red-Team Premise Auditor"`）。
- **Hermes**：调用 `delegate_task`（传入独立上下文与只读检查工具）。
- **Claude Code**：调用 `Task`（`subagent_type: "Explore"` 或只读审阅子智能体）。

---

## 三、发给红队子 Agent 的标准任务 Prompt 模板

主 Agent 在调用子 Agent 时，**严禁把自己的倾向性辩护传过去**，必须按以下客观格式投递任务：

```markdown
你现在的角色是【独立红队架构审阅员（Red-Team Premise Auditor）】。
你的唯一任务是：结合本地代码库和客观技术边界，找出以下拟定方案中的致命前提错误、不存在的 API、并发/状态死锁或安全漏洞。

### 1. 用户的真实底层目标（X）
[用一句话客观描述用户最终想达成的效果]

### 2. 当前拟定的实现方案 / 排错假设（Y）
[列出拟调用的核心 API、修改的文件路径、数据流转步骤]

### 3. 你的核验要求
1. 必须先用 read_file / grep 检查涉及的本地源码、依赖版本或配置文件，禁止凭记忆猜测。
2. 只回答三个问题：
   - 判定结果：🟢 可行 / 🟡 有隐性深坑 / 🔴 根本走不通
   - 核心证伪依据：哪一行代码、哪一个接口边界或哪一条业务状态流转会导致该方案失败？（必须附文件路径与行号证据）
   - 最小替代路径：如果为 🔴 或 🟡，指向目标 X 的最简正确路径是什么？
3. 如果方案完全可行（🟢），直接回复“🟢 未发现致命前提缺陷”即可，禁止为了挑刺而挑刺。
```

---

## 四、主 Agent 收到红队反馈后的裁决规则

1. **红队返回 `🟢`**：主 Agent 直接落地执行，无需向用户展示红队审阅的中间过程（保持零打扰）。
2. **红队返回 `🟡` 或 `🔴`（附带确凿代码/文档证据）**：主 Agent 立即采纳红队证据，按 `SKILL.md` 的「结论先行」模板向用户踩刹车并给出正道方案。
3. **主 Agent 与红队判断分歧**：将双方的核心证据并列（控制在 5 行以内）呈交用户做最终拍板。
